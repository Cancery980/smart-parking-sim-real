# 课堂演示与答辩

这份脚本用约 5 分钟展示可运行功能、异常处理和有记录的对照实验。重点是让老师看到实际结果及其依据，不承诺分数。以下预期对应随包模型与 `parking_hu.reference_planner:Planner`；参考规划器不是梁可已提交的个人代码。梁可接入自己的模块后，应重新核对演示和验收结果。

## 课前准备

提前启动本地程序，确认显示“感知可用”，浏览器窗口和启动窗口都保持打开。把本页、[I01 对照结果](../reports/i01_pairing/RESULTS.md) 和 [实际验收记录](../reports/e2e/results.json) 预先打开。免安装版默认本机端口为 8766，源码版默认 8765；现场使用已启动的地址，不在讲解时安装依赖或训练模型。

下面的场景不是临场挑选。`boundary_50003` 已与冻结缓存核对，当前生成器在相同场景和种子下生成相同车辆实体；常规场景 `91004` 与 E04 输入一致。停车偏离采用已验证的空场交互流程，避免背景车辆占用目标。E06 脚本曾预先清理 P002 的背景冲突，因此**仅在界面输入“常规停车 / 91006”不等于复现完整 E06**，本脚本不使用这一捷径。

## 五分钟操作顺序

### 0:00—0:30 展示真实检测

点击右下角“**重置会话与场景**”，恢复常规停车、种子 `42`；取消“无障碍车位”和“必须充电”的勾选。打开地图上方的“**检测框**”，点击“**重新检测**”，等“感知可用”后指向车辆框及置信度。

可以说：“图片是程序生成的二维仿真帧；这里确实调用本地 YOLO，再由检测框计算车位占用，没有用真值直接填状态。”已保存的真实 UI 验收中，这一初始场景保留 30 个车辆框。现场显示以当前实际推理为准。

### 0:30—1:15 展示跨位证据与三态

在地图下方将“场景”选为“**边界与跨位**”，种子填 `50003`，点击“**更新场景**”。保留“检测框”和“占用状态”图层，指向上排的 **P043、P044**。

冻结记录中，P043 为占用，P044 为不确定；全场为 **23 空闲、22 占用、7 不确定**。跨入 P044 的框置信度约 **0.983**，因此这个例子展示的是“跨位几何证据”，不是刻意制造的低置信度。

选“**模拟车辆 C · 有无障碍资格**”，勾选“无障碍车位”，不勾“必须充电”，偏好保持“少走路”，点击“**申请推荐车位**”。已冻结的同条件三态结果为 `occupancy_uncertain`，不推荐 P044；末尾再展示二态误荐 P044 的缓存结果。日常界面只使用三态，不寻找不存在的“切换二态”按钮。

### 1:15—1:55 展示资格规则

保持无障碍需求，改选“**模拟车辆 A · 燃油车**”，再次点击“**申请推荐车位**”，展示无资格的中文拒绝提示。这里拒绝的依据是登记资格，不能从车辆外观判断资格。

接着把场景改为“**常规停车**”、种子 `91004`，点击“**更新场景**”；改选“**模拟车辆 C · 有无障碍资格**”，保持仅无障碍需求，点击“**申请推荐车位**”。E04 的实际结果是推荐 **P044**。展示合法成功后，点击“**取消本次推荐**”，回到空闲会话。

可以说：“需求与资格是两个字段。专用位条件不满足时不会自动放宽成普通位；换车后也必须重新提交。”

### 1:55—2:45 展示推荐与实际分开记录

将场景设为“**空场**”、种子 `43001`，点击“**更新场景**”。选择“**模拟车辆 A · 燃油车**”，取消两个需求勾选，选择“少走路”，点击“**申请推荐车位**”。已验证的空场流程推荐 **P035**。

点击地图里的 **P001**，确认右侧“实际停入车位”已变为 P001，再点击“**确认已停入此车位**”。状态进入已停车，P001 标记为“实际”，P035 标记为“原推荐”；确认后会重新运行检测。

可以说：“推荐是建议，人工确认记录才是实际停车事实。我们保留偏离提示，寻车不会继续追着原推荐走。实际位置若与已有车辆冲突，则拒绝提交。”

### 2:45—3:25 手动点选起点并寻车

点击“**⌖ 在地图上点选起点**”，在电梯**左侧的绿色人行通道**上点一下，靠近 `(42.6, 4.0)` 米；不要点深色电梯矩形内部。点击“**生成寻车路线**”。

展示绿色人行路线到达 P001 外的接近点 **`(6.25, 0.7)`**，而不是车辆中心。若使用精确电梯起点，距离为 **39.65 米**；手点位置略有偏移，实际距离会随之变化。点错到通道外时应显示中文失败，可用“**从电梯出发**”恢复合法起点再生成。

可以说：“这里是手动输入位置，不是自动定位。路线使用当前帧的车辆障碍，包括目标车辆自己的检测框。”

### 3:25—4:10 展示场景更新与路线失效

保持 P001 已停车，将场景改成“**常规停车**”、种子 `43003`，点击“**更新场景**”。展示旧路线消失、当前没有有效路线，但实际停车仍为 **P001**。随后再次点击“**生成寻车路线**”，使用新帧重新计算。

这条“换背景后保留实际位，再从电梯寻车”的流程已在真实 UI 验收中通过。不要把更新前的路线截图说成更新后的计算结果。

可以说：“场景版本变化就使旧路线失效；已确认的停车事实保留。若当前新场景确实无路，正确行为是解释无路，不是拼接一条旧路线。”

### 4:10—5:00 展示公平对照与结论

点击页面顶部“**实验与交接报告 ↗**”，或切换到课前打开的 [I01 结果](../reports/i01_pairing/RESULTS.md)。指明：**30 个独立场景，每景两种偏好，共 60 个配对请求；B/S 各运行 60 次，产生 120 行结果**，不是 120 个独立场景。

| 冻结结果 | 二态 B | 三态 S |
| --- | ---: | ---: |
| 成功推荐 R / 请求 N | 60 / 60 | 58 / 60 |
| 假空位推荐 F / R | 9 / 60，15.00% | 0 / 58，0.00% |
| 有效推荐 V / N | 51 / 60，85.00% | 58 / 60，96.67% |
| 未推荐 / N | 0 / 60，0.00% | 2 / 60，3.33% |

可以说：“两组共用图像、检测缓存、资格、路网、排序和全部保留车框障碍，只改变占用规则。这批合成场景中三态减少了假空位推荐，同时拒绝了两个请求；我们不把它说成现实场景的普遍提升。”结合 `boundary_50003` 的 P044，解释一次具体差异。

进一步追问时说明：9个被避免的二态误荐请求都来自跨位组，其中7个变成有效推荐、2个未推荐。常规和遮挡组各20个请求，两策略结果相同；没有把无差异场景从总样本中删除。

## 老师可能问的问题

**1. 原预训练模型为什么没识别出来，后来做了什么？**

预训练探索实际运行了 24 张图，记录为 TP=0、FP=0、FN=514，召回率为 0；没有正预测，精确率记为 N/A。合理解释是俯视程序绘图与原预训练数据外观不同，但本项目没有对失败原因做因果消融。随后用独立训练/验证划分适配合成域，测试前冻结参数，再用 30 个留出场景评测。不能只展示微调后的成绩，隐藏前期失败。[探索记录](../reports/vision_pretrained_exploration.json)、[训练配置](../reports/vision_training_config.json)

**2. 场景是自己生成的，会不会直接把答案交给算法？**

检测器只读图片；规划上下文只有地图、感知快照、登记车辆和会话，没有真值占用。真值用于渲染与标注、离线计分，以及确认停车时检查实体冲突；确认冲突检查不会补写检测结果。可以点击“导出当前快照”检查实际接口数据。[接口约定](CONTRACT_V1.md)

**3. 有了 unknown，是不是就不会漏检或错荐？**

不是。unknown 只能处理已经保留下来的模糊证据；完全没有检出的车辆仍可能让车位显示为观测空闲。此次留出集的 59 个 unknown 记录对应跨位占用证据，不能据此说所有现实漏检都会被捕获。30 个缓存共607个检测，最低置信度约0.9521，没有0.20至0.50之间的弱置信框，因此弱置信分支本轮只有规则验证，实测收益来自高置信框的跨位几何证据。0.20、0.50 和 5% 是冻结的工程规则，不是最优阈值证明。[视觉评测](../reports/vision_metrics.json)

**4. 为什么要同时报告覆盖率，怎样保证二态比较公平？**

如果只靠拒绝所有请求，就可能得到没有错荐的表面结果，所以固定 N=60，失败请求仍保留。两组只改占用规则，不删掉二态的障碍检查。此次总推荐覆盖从 100% 降到 96.67%，有效推荐率从 85% 升到 96.67%；两者分母和含义不同。R 为 0 时假空位率写 N/A，不能写成 0% 的胜利。[冻结请求](../reports/i01_pairing/frozen_requests.json)、[逐请求明细](../reports/i01_pairing/paired_requests.csv)

**5. YOLO 和 A* 都是已有技术，项目做了什么？**

检测复用 Ultralytics，参考规划复用 NetworkX A*，几何检查使用 Shapely；没有宣称发明新检测网络或寻路算法。本项目开发的是三态占用与资格约束、双偏好、版本一致性、实际停车和寻车的组合流程，并用只改变占用规则的配对实验评估增量。PythonRobotics 用作算法参考，未把它的网格示例直接当作本项目的有向路网。[复用与交接](PLANNER_HANDOFF.md)、[文献依据](PAPERS.md)

**6. 两个人怎样分工，代码能直接接吗？**

胡轩铭提供场景与视觉感知、评测、界面和会话；梁可负责需求资格、优选和路径规划等约定部分。通过 `plan(context, request)` 与 `find_vehicle(context, request)` 两个方法对接，启动时指定模块名。当前随包参考规划器保证演示可运行；外部接线样例的通过结果不能冒充梁可尚未交付的个人实现。替换后应重新运行指向该模块的契约、真实端到端与配对验收。[接线指引](梁可从这里开始.md)

**7. 实际停车与推荐不同，或者确认后检测失败怎么办？**

确认前检查会话、版本和实体冲突，通过后一次提交实际位置。偏离推荐只产生提示，寻车使用实际 ID。提交后的检测失败不撤销已经确认的停车事实；感知不可用时暂停依赖感知的新规划，界面明确提示。检测遗漏也不能覆盖实际记录或被计作识别成功。[会话与接口](CONTRACT_V1.md)

**8. 能不能直接用于真实停车场？测试很好是否说明已经能部署？**

本次是同一固定地图、同一程序绘图器的不同留出种子。检测测试中 607 个真值目标在当前阈值与匹配口径下全部匹配，仍然只是合成域内的结果；没有在真实监控照片或另一停车场上验证。真实部署还需要相机标定、视角与光照适配、独立实景数据等工作。路线也只是图上的引导线，没有验证车辆转弯半径、车身净空、自动定位或自动驾驶。[视觉范围说明](../reports/vision_report.md)

## 备用证据与现场处理

- 若要补充充电案例：空闲会话下选“常规停车 / `91003`”，车辆 B，只有“必须充电”为真；E03 的已存结果推荐 P050。燃油车 A 提出相同充电要求应被拒绝。
- 若问“全满怎么办”：空闲会话下选“普通位全满 / `91005`”，车辆 A、无特殊需求；E05 已存结果为 `no_available_spot`。不要为了得到成功推荐而私自换掉这张图。
- 若问“旧版本能否确认”：展示 E08 记录。其原场景为常规 `91008`，更新到 `92008` 后，旧确认被 `stale_scene` 拒绝。课堂主线已演示寻车路线失效，这份记录补充的是确认写入保护。
- 如果现场结果不同，先说明当前模型、场景、种子和规划模块，保留失败提示；可以展示原有验收作为历史证据，但不能把历史记录称作这次现场运行通过。
